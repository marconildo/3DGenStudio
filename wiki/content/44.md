# Server Deployment

3D Gen Studio can run as a **shared server** so a team works from one machine instead of scattered local folders. The server holds projects, assets, workflow definitions and user accounts — nothing else. ComfyUI, the mesh and motion tools, and every third-party API key stay on each user's own machine.

Shared does not mean *common*: everything belongs to whoever created it, and nobody sees anyone else's work except administrators. See **Who sees what** below.

That split is what makes the server cheap to host: it needs **no GPU** and very little CPU. It is the same `server.js` you already run locally, started with the environment variable `GENSTUDIO_MODE=server`.

There are two ways to install it, both covered below:

- **Synology NAS**, using Docker.
- **Windows Server**, using Node.js directly, with no Docker.

## What runs where

| | Shared server | Each user's machine |
| --- | --- | --- |
| Projects, cards, graphs, boards | ✅ | |
| Assets — images, meshes, thumbnails, motions | ✅ | |
| Workflow **definitions** | ✅ | |
| User accounts and roles | ✅ | |
| Ownership of everything above | ✅ | |
| ComfyUI, and every workflow **run** | | ✅ |
| Mesh, rig and motion services | | ✅ |
| API keys (Tripo, Hitem3D, Tencent…) | | ✅ |

A generated asset is produced on the user's own GPU and then uploaded to the server. If the server is unreachable when a run completes, the result is spooled to disk and retried — a long generation is never lost to a server blip.

## Who sees what

Every project, asset and workflow on the server belongs to one user. Signed in as yourself you see your own work and nothing else; **administrators see everything**. A single-user desktop install has no accounts, so none of this applies there and it behaves exactly as it always did.

Ownership is assigned by three rules:

| What you make | Who owns it |
| --- | --- |
| A project | You. |
| An asset **inside a project** | The **project's** owner — not necessarily you. An administrator adding an asset to Bruno's project is acting on Bruno's behalf, so it lands in Bruno's library where he can actually see it. |
| An asset imported into the library, with no project | You. |
| An edit or a version | Whoever owns the asset it came from, so a version chain never splits between two libraries. |

The Projects page shows the owner's name under each project card. It appears only when a server supplies one, so a desktop card is unchanged.

### Workflows are personal too

A ComfyUI workflow is written against one person's models and node packs, so each user has their own library. Importing the bundled templates gives *you* a copy and leaves everyone else's alone.

The trade-off: a teammate opening your project sees the assets you generated, but cannot press Run on a node that uses your workflow — they get *"This workflow belongs to another user. Import your own copy to run it."* They can import the same template and point the node at their copy.

Re-importing a workflow you already have **updates it in place**, keeping its id. That matters because graph nodes, Batch stages and Kanban cards all store that id: a workflow that got a new id on every reinstall would quietly break every node pointing at it.

### Two things worth knowing

**Anything created before ownership existed has no owner, and stays visible to everyone.** Nothing disappeared, but nothing is claimed either. To assign it all to one person, stop the server and run:

```sql
UPDATE Projects SET ownerId = (SELECT id FROM Users WHERE login='Bruno') WHERE ownerId IS NULL;
UPDATE Assets   SET ownerId = (SELECT id FROM Users WHERE login='Bruno') WHERE ownerId IS NULL;
```

**A direct asset URL is not owner-checked.** Listings are scoped, so there is no way to *discover* another user's files — but a link someone pastes to `/assets/images/….png` will open for any signed-in user. Treat ownership as workspace separation between colleagues, not as a security boundary against them.

## Before you start

### The two required secrets

The server refuses to start if either of these is wrong, rather than coming up half-configured. That is deliberate and much easier to diagnose than the alternative.

| Variable | Rule | Why |
| --- | --- | --- |
| `GENSTUDIO_JWT_SECRET` | At least 16 characters | Sessions are validated against it. **Keep it** — changing it signs every user out. A per-restart secret would do that on every deploy, so the server will not invent one for you. |
| `GENSTUDIO_ADMIN_PASSWORD` | At least 8 characters | Creates the first administrator, once, while the user table is still empty. If it cannot create that account the server exits — the alternative was a healthy server with no login on it. |

Generate the secret anywhere Node is installed:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

### Which database

A shared server runs on **PostgreSQL**. A desktop install runs on **SQLite** and always will — one file, nothing to install, nothing to administer.

The reason is not that SQLite is slow. It is that the whole server shares a *single* database connection, so every request waits its turn behind every other one, no matter how many people are using it. That is invisible with two people and obvious with ten. PostgreSQL gives the server a pool of connections, so requests genuinely run at the same time.

Two ways to get one, and neither asks you to administer a database:

| | How | When |
| --- | --- | --- |
| **Docker Compose** | `docker-compose.yml` already includes it. `docker compose up -d` starts both. | Any Docker host, including the NAS below. |
| **Managed by 3D Gen Studio** | `GENSTUDIO_DATABASE=embedded`. The app downloads PostgreSQL (about 330 MB, once) into `data/`, creates its own cluster and runs it as a child process. | A bare-metal server without Docker — the Windows Server route below. Windows and macOS only. |

To point at a PostgreSQL you already run, set `GENSTUDIO_DATABASE_URL` to its connection string instead; that always wins.

Leaving both unset keeps the server on SQLite. That is fine for one or two people and will not stay fine.

### The rest

| Variable | Default | Notes |
| --- | --- | --- |
| `GENSTUDIO_MODE` | `local` | Must be `server`. |
| `GENSTUDIO_ADMIN_LOGIN` | `admin` | The first administrator's login. |
| `PORT` | `3001` | The server binds all interfaces. |
| `TRUST_PROXY_HEADERS` | on | Set to `0` whenever the server is reachable directly — see the warning below. |
| `PUBLIC_BASE_URL` | — | Only behind a reverse proxy, e.g. `https://studio.example.com`. |
| `GENSTUDIO_DATABASE_URL` | — | An existing PostgreSQL, e.g. `postgres://genstudio:secret@db:5432/genstudio`. Set by `docker-compose.yml` for you. |
| `GENSTUDIO_DATABASE` | — | `embedded` to have 3D Gen Studio install and run PostgreSQL itself. Ignored when `GENSTUDIO_DATABASE_URL` is set. |
| `GENSTUDIO_DB_POOL_MAX` | `10` | Connections held open. This is the ceiling on how many requests are served at once — raise it for a larger team. |
| `GENSTUDIO_SLOW_QUERY_MS` | `500` | Log any statement slower than this. `0` turns it off. |
| `GENSTUDIO_ALLOW_EMPTY_DATABASE` | — | `1` to start with an empty PostgreSQL while a populated `app.db` is still present. See *Moving an existing server to PostgreSQL*. |

> **Set `TRUST_PROXY_HEADERS=0` on a directly-reachable server.**
> `X-Forwarded-*` headers are trusted by default, and the resulting host goes into every asset URL the API hands out. Left on, a client can send `X-Forwarded-Host: evil.example.com` and the API will answer other users with `https://evil.example.com/assets/…`.
> Behind a proxy, set `PUBLIC_BASE_URL` instead and leave this at `0`: `PUBLIC_BASE_URL` is read *before* the headers, so nothing can spoof it.

### Where the data lives

Everything worth backing up is in **`data/`** — every image, mesh, thumbnail and motion clip, plus the database if you are on SQLite. The path is derived from the process working directory, so it is always `<working directory>/data`.

Moving to PostgreSQL changes only where the *rows* live. **Asset files stay on disk exactly as before**, referenced by path — so `data/` remains stateful and still needs backing up, now alongside the database.

## Install on a Synology NAS (Docker)

A NAS is a good host for this: the server is I/O-bound rather than compute-bound, and the data sits on the array you already back up.

### 1. Check the NAS can run it

You need **DSM 7.2 or newer** for Container Manager and its Projects interface. On DSM 7.0–7.1 the older Docker package works, but you drive Compose over SSH instead of through the interface.

Then check the CPU architecture, because it decides how you build. Enable SSH (**Control Panel → Terminal & SNMP**), connect, and run:

```sh
uname -m
```

- `x86_64` — the common Intel/AMD models. Build normally.
- `aarch64` — 64-bit ARM. Build for ARM, see step 2.
- Anything else (`armv7l`, `armv5tel`) — the Node base image has no build for it. Use the Windows guide on another machine instead.

### 2. Build the image on your PC

The build runs `npm ci`, a Vite bundle and a from-source compile of SQLite. That is slow on NAS hardware and can run out of memory — and the NAS does not have the repository anyway. Build where the code is.

The repository has a script for each architecture, and either produces two tars — the application and the database image. Run `docker_build_nas_x86.bat` or `docker_build_nas_arm64.bat`, or do it by hand.

If `uname` said `x86_64`, from the repository root:

```sh
docker compose build
docker pull postgres:17-alpine
docker save 3dgenstudio-server:latest -o genstudio-server.tar
docker save postgres:17-alpine -o genstudio-postgres.tar
```

If it said `aarch64`:

```sh
docker buildx build --platform linux/arm64 -t 3dgenstudio-server:latest --load .
docker pull --platform linux/arm64 postgres:17-alpine
docker save 3dgenstudio-server:latest -o genstudio-server.tar
docker save postgres:17-alpine -o genstudio-postgres.tar
```

Skip the `postgres` lines if you are pointing the server at a PostgreSQL the NAS already runs — see *Using a PostgreSQL the NAS already runs* in step 5.

> **Install the emulator before the ARM build, or it dies on its first line.**
> Cross-building runs every command in the image under emulation, and Docker Desktop does not always register the handlers for it. Without them the build pulls the ARM image fine and then fails on the first `RUN` with `exec /bin/sh: exec format error` — which reads like a broken Dockerfile but actually means *"this machine cannot execute ARM binaries"*.

Check what your builder can really target:

```sh
docker buildx ls
# linux/arm64 must appear in the PLATFORMS column
```

If it is missing, register the handlers once — they last until Docker Desktop's VM is reset:

```sh
docker run --privileged --rm tonistiigi/binfmt --install arm64
```

Everything then runs emulated, so expect the ARM build to take several times longer than a native one — the SQLite compile especially. If `uname -m` said `x86_64`, do not use this path at all.

You will also see `CopyIgnoredFile: Attempting to Copy file "." that is excluded by .dockerignore` during any build. It is harmless: `.dockerignore` is an allowlist that excludes `*` and re-includes each needed path, so BuildKit warns about the builder's `COPY . .` sitting against a blanket exclusion. The re-included paths still copy.

### 3. Load the image onto the NAS

The build scripts produce **two** tars: `genstudio-server.tar` and `genstudio-postgres.tar`. Both are needed — the NAS has no way to fetch the database image on its own, and a project whose image is missing simply never starts.

Copy both to the NAS with File Station — `/volume1/docker/` is a sensible place. Then either use **Container Manager → Image → Add → Add from file** for each, or over SSH:

```sh
sudo docker load -i /volume1/docker/genstudio-server.tar
sudo docker load -i /volume1/docker/genstudio-postgres.tar
```

### 4. Create the data folder and hand it to uid 1000

This is the step that costs people an evening. The container runs unprivileged as the `node` user, **uid 1000**. A folder created through DSM belongs to `root`, so the server cannot create its database and the container sits in a restart loop.

```sh
sudo mkdir -p /volume1/docker/genstudio/data
sudo chown -R 1000:1000 /volume1/docker/genstudio
```

If SSH is not an option, use a Docker-managed **named volume** instead of a bind mount — the image already sets the ownership inside it, so there is nothing to fix. The cost is that the files are then invisible to File Station and Hyper Backup cannot reach them directly. On a NAS, the bind mount is usually worth the one `chown`.

### 5. Create the project

**Container Manager → Project → Create.** Set the path to `/volume1/docker/genstudio`, choose *Create docker-compose.yml*, and paste this:

```yaml
services:
  db:
    image: postgres:17-alpine
    container_name: genstudio-db
    restart: unless-stopped
    environment:
      POSTGRES_DB: genstudio
      POSTGRES_USER: genstudio
      POSTGRES_PASSWORD: "<choose a password>"
    volumes:
      # A named volume, not a bind mount. The database image runs as uid 70
      # while the app runs as 1000, so a bind mount would need a chown of its
      # own and gets it wrong silently. Nothing here needs to be browsable in
      # File Station -- back it up with pg_dump, not by copying files.
      - genstudio-db:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U genstudio -d genstudio"]
      interval: 5s
      timeout: 5s
      retries: 20

  genstudio-server:
    image: 3dgenstudio-server:latest
    container_name: genstudio-server
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    ports:
      - "3001:3001"
    environment:
      GENSTUDIO_MODE: server
      # Same password as above. Without this the server falls back to SQLite,
      # comes up perfectly healthy, and serves one writer to the whole team.
      GENSTUDIO_DATABASE_URL: "postgres://genstudio:<the same password>@db:5432/genstudio"
      GENSTUDIO_JWT_SECRET: "<the 64 hex characters from Before you start>"
      GENSTUDIO_ADMIN_LOGIN: admin
      GENSTUDIO_ADMIN_PASSWORD: "<at least 8 characters>"
      TRUST_PROXY_HEADERS: "0"
    volumes:
      - /volume1/docker/genstudio/data:/app/data

volumes:
  genstudio-db:
```

> **The log tells you which database you got.**
> On startup the server prints either `DEBUG: database is PostgreSQL` or `DEBUG: database is SQLite at /app/data/app.db`. If it says SQLite, `GENSTUDIO_DATABASE_URL` did not reach the container — the server does not guess, and it does not fail either, because SQLite is a perfectly valid configuration for one person.

> **Replacing an existing SQLite server, without keeping its data?**
> Delete `app.db` from `/volume1/docker/genstudio/data/` first (`app.db-wal` and `app.db-shm` too). Otherwise the server refuses to start: an empty database next to a populated `app.db` is indistinguishable from having lost everything, so it stops and says so rather than serving an empty workspace. To keep the data instead, see *Moving an existing server to PostgreSQL* below; to start empty without deleting anything, set `GENSTUDIO_ALLOW_EMPTY_DATABASE: "1"`.

#### Using a PostgreSQL the NAS already runs

If you have the SynoCommunity **PostgreSQL** package installed, use it instead of the `db` service — drop that service, the `depends_on` block and the `volumes:` section, and keep only `GENSTUDIO_DATABASE_URL`. You then do not need `genstudio-postgres.tar` at all.

Create a database and a role for the app first. A dedicated, non-superuser role is enough — the app creates its own tables and needs no extensions:

```sh
psql -h 127.0.0.1 -p 5443 -U admin -c "CREATE ROLE genstudio LOGIN PASSWORD '<a password>';"
psql -h 127.0.0.1 -p 5443 -U admin -c "CREATE DATABASE genstudio OWNER genstudio;"
```

Then point the container at it, using the NAS's LAN address rather than `localhost` — inside a container `localhost` is the container:

```yaml
      GENSTUDIO_DATABASE_URL: "postgres://genstudio:<the password>@192.168.1.10:5443/genstudio"
```

Two things to check if it cannot connect:

* **`listen_addresses`** must include the NAS's LAN address, not just `localhost`.
* **`pg_hba.conf`** must allow the Docker bridge network (commonly `172.16.0.0/12`) with `scram-sha-256`. Both files live in the package's data directory; reload PostgreSQL after editing.

> **Special characters in the password have to be URL-encoded.** `@`, `/`, `:`, `#` and `?` all mean something in a URL — write them as `%40`, `%2F`, `%3A`, `%23`, `%3F`. `!` is safe as-is. In a Compose file a literal `$` must also be doubled to `$$`.

> **Do not reuse the repository's `docker-compose.yml` here.**
> That file reads its secrets from a `.env` beside it, via `${GENSTUDIO_JWT_SECRET}`. On a normal Docker CLI a missing value makes Compose refuse to start and say so; **Container Manager substitutes an empty string instead**. The container then starts and dies on the app's own check with `GENSTUDIO_JWT_SECRET must be set to at least 16 characters` — which reads like a bad secret rather than a missing one.
> The tell: `GENSTUDIO_MODE` is a literal in that file and arrives fine, while every `${…}` value is blank. Keep the values inline, as above.

> **Environment changes need a rebuild, not a restart.**
> Whenever you edit those variables, use **Project → Action → Build**. Stop/Start reuses the existing container with its original environment, so a correct fix will look like it did nothing.

### 6. Verify

From any machine on the network:

```sh
curl http://NAS-IP:3001/api/health
{"ok":true,"mode":"server","version":"3.0.0"}
```

Then open `http://NAS-IP:3001` in a browser. You should get the sign-in screen. If the page is blank, see **Troubleshooting** at the end of this page.

### 7. Firewall and HTTPS

**Control Panel → Security → Firewall**: allow TCP 3001 for your LAN. If the NAS firewall is off entirely, there is nothing to do.

For HTTPS, use the DSM reverse proxy — **Control Panel → Login Portal → Advanced → Reverse Proxy**. Point `https://studio.example.com:443` at `localhost:3001`, and add one line to the compose file:

```yaml
      PUBLIC_BASE_URL: "https://studio.example.com"
```

The app pushes changes to open clients over a Server-Sent Events stream at `/api/events`. Response buffering in a proxy delays that stream without breaking anything else, so *"everything works but other people's changes appear late"* points here first.

## Install on Windows Server (Node.js)

No Docker and no container runtime — Node runs `server.js` directly and a service wrapper keeps it alive across reboots. SQLite ships a prebuilt Windows binary, so no compiler is involved.

### 1. Install Node.js

Get the Node **24.x** x64 MSI from [nodejs.org](https://nodejs.org) — the same major version the Docker image uses. Confirm it, and that npm came along at version 11:

```sh
node -v   # v24.x
npm -v    # 11.x
```

### 2. Copy only what runs

Do not clone the repository onto the server. With `comfyui/` and `thirdparty/` it is tens of gigabytes, none of which the server touches.

On your development machine, build the frontend:

```sh
npm run build
```

Then copy exactly this set into `C:\GenStudioServer\`:

```
package.json          server.js         gateway.js       mcp\
package-lock.json     storage.js        dataStore.js     wiki\
version.json          wikiStorage.js    uploadQueue.js   dist\
                      auth.js           logs.js
                      serverMode.js     meshPivot.js
```

This is the same set the Docker image ships. `node tools/check-packaged-modules.mjs` is what keeps that list honest — run it if you ever add a backend module.

### 3. Install the production dependencies

```sh
cd C:\GenStudioServer
npm ci --omit=dev
```

About 625 packages, roughly 20 seconds. `--omit=dev` skips Vite and the Electron builder, because the frontend is already built.

### 4. Write the start script

Save as `C:\GenStudioServer\start-server.cmd`:

```bat
@echo off
cd /d "%~dp0"
set GENSTUDIO_MODE=server
set PORT=3001
set GENSTUDIO_JWT_SECRET=<the 64 hex characters>
set GENSTUDIO_ADMIN_LOGIN=admin
set GENSTUDIO_ADMIN_PASSWORD=<at least 8 characters>
set TRUST_PROXY_HEADERS=0
node server.js
```

> **The working directory is load-bearing.**
> `cd /d "%~dp0"` is not boilerplate. The database and every asset live in `<working directory>\data`, so starting from somewhere else creates a second, empty database and the server looks like it lost everything.

### 5. Test it in the foreground

Run the script from a console. You are looking for the seeding line and the port banner:

```
👤 Seeded initial administrator "admin" from the environment
🚀 3D Gen Studio Backend running at http://localhost:3001
📁 Local Workspace: C:\GenStudioServer\data
🖥️  Serving bundled UI from dist/
```

Check it, then stop with `Ctrl+C`:

```sh
curl http://localhost:3001/api/health
```

### 6. Install it as a service

**NSSM** is the least surprising option: it restarts the process if it dies and captures output to a file, neither of which Task Scheduler does well.

```bat
nssm install GenStudioServer "C:\Program Files\nodejs\node.exe"
nssm set GenStudioServer AppDirectory "C:\GenStudioServer"
nssm set GenStudioServer AppParameters "server.js"
nssm set GenStudioServer AppEnvironmentExtra ^
  GENSTUDIO_MODE=server ^
  PORT=3001 ^
  GENSTUDIO_JWT_SECRET=<secret> ^
  GENSTUDIO_ADMIN_LOGIN=admin ^
  GENSTUDIO_ADMIN_PASSWORD=<password> ^
  TRUST_PROXY_HEADERS=0
nssm set GenStudioServer AppStdout "C:\GenStudioServer\logs\out.log"
nssm set GenStudioServer AppStderr "C:\GenStudioServer\logs\err.log"
nssm start GenStudioServer
```

`AppDirectory` is the same working-directory rule as the batch file — it is what decides where `data\` ends up.

Without NSSM: Task Scheduler, a task triggered *At startup*, **Run whether user is logged on or not**, action = `start-server.cmd`. Whichever account runs it needs write access to `C:\GenStudioServer`.

### 7. Open the firewall

```powershell
New-NetFirewallRule -DisplayName "3D Gen Studio Server" `
  -Direction Inbound -Protocol TCP -LocalPort 3001 -Action Allow
```

For HTTPS, put IIS with Application Request Routing (or any proxy you already run) in front, and set `PUBLIC_BASE_URL` to the public address — same as the Synology guide, step 7.

## Once it is running

### Replace the seeded administrator

Sign in with the seeded account, then **Settings → Server** to create your own administrator, and *disable* the seeded `admin`. Create the new one first: the server refuses to disable or demote the last enabled administrator.

The user manager creates accounts, changes roles and enables or disables people, but it **cannot change an existing password**. The API can — `PATCH /api/users/:id` with `{"password":"…"}` as an administrator — so use that if you would rather keep the `admin` account.

> **Disable people who leave; do not delete them.**
> Deleting a user removes only the account row. Their projects, assets and workflows stay on disk still stamped with an id that no longer matches anybody, so they vanish for every ordinary user and only an administrator can still see them. Disabling blocks sign-in and leaves ownership intact. If you do delete someone, reassign their work first:
>
> ```sql
> UPDATE Projects SET ownerId = <newOwner> WHERE ownerId = <oldOwner>;
> UPDATE Assets   SET ownerId = <newOwner> WHERE ownerId = <oldOwner>;
> UPDATE WorkflowConfigs SET ownerId = <newOwner> WHERE ownerId = <oldOwner>;
> ```

### Roles

| Role | Can do |
| --- | --- |
| **Administrator** | Everything, everyone's — plus user management. The only role that sees other people's projects and assets. |
| **User** | Read and write **their own** projects, assets and workflows. |
| **Viewer** | Read only, and only their own. Writes are refused with *"Your role is read-only"*. |

The server enforces roles and ownership regardless of what the interface offers, and the banner under the header explains why an action is unavailable. Reaching for something that belongs to someone else returns **403** with a message naming the reason — deliberately not 404, because "no such project" reads as data loss when the truth is "that one is Bruno's".

### Connect the desktop apps

On each user's machine: **Settings → Server**, enter the address `http://host:3001` and their login. From then on, *their* projects and assets come from the server while ComfyUI, the mesh and motion tools and their API keys stay local.

The password never reaches the browser. It is posted to that user's own backend, which signs in on their behalf and holds the session token itself.

### Browse from a web browser

The server also serves the interface, so anyone can open `http://host:3001` and sign in to browse their projects and assets without installing anything. Generation is unavailable there — ComfyUI and the mesh tools need the desktop app — but everything they have already produced is visible.

### Moving an existing server to PostgreSQL

Do this **before** the first start on the new database. Only rows move; asset files are not touched.

The server will not let you skip it. Pointed at an empty PostgreSQL while a populated `app.db` is still there, it refuses to start and says so — because an empty workspace and a lost workspace look identical from the UI, and the natural response to the second one is to start recreating work by hand.

Docker:

```sh
docker compose up -d db
docker compose run --rm --entrypoint node genstudio-server \
  tools/migrate-sqlite-to-postgres.mjs --from ./data/app.db --to "$GENSTUDIO_DATABASE_URL"
docker compose up -d
```

Managed by 3D Gen Studio (`--to embedded` starts it and finds its own password):

```sh
node tools/migrate-sqlite-to-postgres.mjs --from ./data/app.db --to embedded
```

It prints a row count per table, verifies every one of them against the committed data, and runs in a single transaction — so either the whole database arrives or nothing does. Add `--dry-run` to read and count without writing.

Keep `app.db` until you are satisfied. Nothing deletes it, and it is the only copy of the old state.

### Backups

There are two halves, and a backup of one without the other is not a backup.

**Asset files.** Back up `data/`. These are ordinary files and can be copied while the server runs.

**The database.**

* *PostgreSQL* — use `pg_dump`, which is consistent without stopping anything:

  ```sh
  docker compose exec db pg_dump -U genstudio genstudio > genstudio.sql
  ```

  Do not simply copy the data directory of a running cluster.

* *SQLite* — back up `data/app.db` with the server **stopped**. It runs in WAL mode, so a copy taken mid-write can be torn. If you must copy it live, take `app.db`, `app.db-wal` and `app.db-shm` together: a database file without its WAL is missing recent writes.

### Updating

Rebuild and reload the image, or copy the changed files and restart the service.

One thing to remember: `storage.js`, `serverMode.js` and `auth.js` run on **both** sides. Change any of those and you must update the server **and** rebuild the desktop app, or the fix will appear not to work.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Exits immediately, log mentions `GENSTUDIO_JWT_SECRET` | The secret is shorter than 16 characters, missing — or, on DSM, blanked by a `${…}` substitution that found no `.env` | Check what actually reached the container: `docker inspect <name> --format '{{range .Config.Env}}{{println .}}{{end}}'`. An empty value means it never arrived — inline the values (Synology, step 5). Otherwise generate a longer secret. |
| Fixed a variable, same error after restarting | The container was restarted, not recreated, so it kept its original environment | Container Manager: **Project → Action → Build**. CLI: `docker compose up -d`, which recreates. |
| A `.env` file is ignored on the NAS | It is really `.env.txt` — File Station and Notepad append the extension and DSM hides it | `ls -la` in the project folder. Inline values avoid the question entirely. |
| *"Could not create the initial administrator"*, then exits | Administrator password shorter than 8 characters | Lengthen it. |
| *"The PostgreSQL database is empty, but …app.db still holds data"*, then exits | The old SQLite data has not been migrated | Run the migration above. If starting empty really is intended, set `GENSTUDIO_ALLOW_EMPTY_DATABASE=1`. |
| Everything is there but the app feels slow under load | The connection pool is the ceiling on concurrent requests | Raise `GENSTUDIO_DB_POOL_MAX`, and check the backend log for `[db] slow query` lines first — they name the statement. |
| Exits with *"A self-contained PostgreSQL build is not available for linux"* | `GENSTUDIO_DATABASE=embedded` is Windows and macOS only | Use Docker Compose, or install PostgreSQL from your package manager and set `GENSTUDIO_DATABASE_URL`. |
| *"Invalid credentials"* with a password you know is right | The account was never created, from an earlier failed seed | Read the startup log for the seeding line. The seed only runs while the user table is empty. |
| Container restart loop, `SQLITE_CANTOPEN` | The bind-mounted data folder is not writable by uid 1000 | `chown -R 1000:1000` on the folder — Synology, step 4. |
| `exec format error` when the container starts **on the NAS** | Image built for the wrong CPU architecture | Rebuild with `--platform linux/arm64`, or check `uname -m` again. |
| `exec /bin/sh: exec format error` during the **build**, on the first `RUN` | The build machine cannot execute ARM binaries — no emulation handlers registered | `docker buildx ls`; if `linux/arm64` is absent, run `docker run --privileged --rm tonistiigi/binfmt --install arm64`. First confirm the NAS really is `aarch64` — on x86_64 a plain `docker compose build` is correct and none of this applies. |
| Build warns `CopyIgnoredFile … excluded by .dockerignore` | Nothing. `.dockerignore` is an allowlist, so the builder's `COPY . .` sits against a blanket `*` exclusion | Ignore it. |
| A project or asset you expected is missing | It belongs to another user | Sign in as its owner, or as an administrator. The Projects page shows the owner under each card. |
| *"This workflow belongs to another user"* when running a node | Workflow libraries are per-user, and the node points at a teammate's copy | Import the same workflow yourself and select your copy on the node. |
| Browser shows a blank page | Stale or missing `dist/` in the deployed copy | Run `npm run build` and redeploy. |
| Interface loads but images and thumbnails are broken | Asset URLs are minted with the wrong host or port | Set `PUBLIC_BASE_URL`. The first request logs the host it resolved — that log line tells you what the server thinks it is. |
| Desktop app suddenly shows no projects | Its session was rejected, so data routes are blocked | **Settings → Server**, sign in again. It blocks rather than falling back to the local database, because showing a different empty workspace reads as data loss. |
| Other people's changes appear late | A reverse proxy is buffering the `/api/events` stream | Disable response buffering for that path, or reach the server directly. |
